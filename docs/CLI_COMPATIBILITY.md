# CLI 协议与版本切换验收

2026-09-16 使用实际 `codex-cli 0.148.0` 和 `0.153.2` 完成以下矩阵。前者为项目原兼容基线，后者为本次维护时安装的版本；不据此承诺更早或未来版本全部兼容。原有部分嵌套 initialize 单元夹具是合成边界测试，不能替代本记录中的真实结果。

## 可复现入口

```bash
npm run verify:cli -- /path/to/old/codex /path/to/new/codex
```

该显式命令不随 `npm run check` 自动执行，也不安装或替换系统 CLI。请按旧到新的顺序传入已准备的可执行文件。每个版本先生成实验 JSON Schema，然后通过完整 PWA 的 isolated/stdio 桥接启动；执行初始化、HTTP 健康/状态检查和实际 `model/list`。相邻版本依次打开同一份新建的临时 SQLite 目录，验证旧版初始化状态可被新版继续使用。

隔离使用官方文档中的命令行 `sqlite_home`、`log_dir` 和 `history.persistence` 覆盖，保留 `HOME`/`CODEX_HOME`；`--strict-config` 校验配置。只创建临时端口、项目、日志、状态数据库和 PWA 数据文件，不写入用户配置，不执行 daemon 管理命令，不创建或写入 Codex 任务。结束后清理本次进程和临时目录。数据目录配置依据见 [OpenAI 官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference#configtoml)。

输出只保留版本、接口/字段名、schema SHA-256 及运行检查摘要；不输出真实任务、模型名称、凭据、初始化中的用户目录或原始 CLI 日志。首次初始化在本次环境约需 20 秒，验收允许最多约 40 秒等候桥接就绪；PWA 自身的 30 秒 RPC 时限保持不变。

## 消息关联字段的实际回传（2026-09-16）

```bash
npm run verify:message-identity -- /path/to/old/codex /path/to/new/codex
```

这个入口与上面的无任务启动验收分开运行。它通过 stdio 启动独立 app-server，使用 `ephemeral: true` 的内存任务和仅监听 loopback 的本地 Responses 测试端点；端点不生成模型输出、不执行工具、不调用外部模型。任务开始前核对临时 provider，收到用户消息后停止轮次并退出临时进程；状态数据库、日志和工作目录独立，`HOME`/`CODEX_HOME` 不变，生产服务及共享 daemon 不受控制。输出只保留版本、字段名和核对结果，不输出任务 ID、正文、凭据或真实路径。

实际 0.148.0 与 0.153.2 都将 `turn/start.params.clientUserMessageId` 原样回传为 `item/started.params.item.clientId`。这证明 `clientId` 是客户端提供的**消息关联标识**；字段本身不能用作服务器认证的设备身份。内存任务不支持 `thread/read(includeTurns: true)`，因此此探针不声称验证了落盘历史或重启后的消息来源。`turn/steer` 同名参数在两版实验 schema 中存在；PWA 的追加路径另由 HTTP 传递回归覆盖，探针未验证追加消息的完整生成周期。

PWA 在运行后端通过 `bridgeCapabilities.clientMessageCorrelation` 明确声明转发支持后，为每次发送生成随机关联标识，新建、继续及追加路径均校验并传递该字段。只更新了静态文件、尚未重载的旧后端维持原有发送方式，避免忽略新字段造成重复气泡。此桥接能力与上游声明的能力矩阵分开，不表示已发现设备身份契约。

已有同任务回声时按标识合并，正文相同但标识不同或缺失时保持独立；仅两端都没有关联标识的旧记录使用既有正文匹配。它不包含登录设备 ID，不作为授权凭据，也不意味着同标识重试会被 Codex 去重。结果未知时仍按原规则核对状态，不能自动重发。

物理设备来源映射仍缺少协议依据，R02 保持待完成。当前版本也没有在已核对的任务字段和方法中提供完整的写入者身份与安全接管契约，R03 保持待完成；不能由消息关联、任务创建来源或 `canAcceptDirectInput` 推导 Windows/手机当前写入者。

随后在独立账号完成原生 0.153.2 的多连接/跨进程实验：同一进程的第二个连接可向当前轮次追加输入；另一进程恢复任务时才遇到 active writer。轮次结束、退订和关闭连接后仍可能冲突，不能把退订当作写入权已经移交。具体步骤和边界见[协议核对记录](PROTOCOL_AUDIT.md#真实多连接与跨进程写入实验)。

配置和传输依据：[官方 app-server 文档](https://learn.chatgpt.com/docs/app-server)、[自定义模型端点](https://learn.chatgpt.com/docs/config-file/config-advanced#custom-model-providers)。上述字段对应关系来自实际 CLI 探针，不是官方页面未给出的设备身份保证。

本阶段完整验证以退出码 0 完成：264/264 测试通过，暂存包 119 个模块、226 处本地导入、158 个清单文件及隐私扫描通过；实际运行的 63 个前端文件、68 个预缓存 URL、登录/CSRF/目录/审批身份均通过。移动 Chrome 同时验证旧后端未声明能力时保持原发送方式，以及新后端声明后两条外部同文消息不会合并到本机发送气泡。Service Worker 为 v112，生产后端未重载。

## 修复与适配边界

- PWA 在初始化时启用 `experimentalApi`，因此协议审计必须使用 `generate-json-schema --experimental` 或 `generate-ts --experimental`；默认 TypeScript 输出会省略 `availableDecisions` 等字段。本轮正是通过实验 schema 复现了之前遗漏的选项限制。
- 当命令审批提供 `availableDecisions`，界面按该列表顺序只展示支持且被允许的选项，后端同样校验。越过列表提交会返回 400 `APPROVAL_DECISION_UNAVAILABLE`，明确尚未发送。字段缺失或为 null 时，保留基础四种决定；显式空列表不回退到全部批准。
- 命令审批的额外文件/网络权限和访问目标同时保留在摘要及二次确认中，审批理由也不会再被命令文本覆盖；可空 command 缺失时仍展示这些请求范围。它们是上游请求信息，不改变 PWA 文件授权范围。
- 规则/网络策略修改等结构化决定尚未提供 UI；不会把它们转换成一次批准或会话批准。仍有基础选项时保留这些选项，否则提示在发起请求的客户端处理。审批响应的现代/旧式映射集中在 `protocol-adapter.mjs`。
- 能力诊断只接受明确布尔声明或精确的能力名称匹配；不从 `goalDisabled` 等子串推断支持，明确布尔声明优先于方法名推测。两版真实初始化均未声明能力，PWA 保持“未声明”，不把 CLI 版本冒充独立协议版本。
- 当前兼容表中的 15 个替代事件拼写均未出现在这两版 schema；它们保留为已有客户端的宽容拼写处理，不再作为“真实旧 CLI 曾发送该事件”的证据。规范方法名及未知事件诊断保持不变。
- 两版另外声明了权限审批、动态工具调用、MCP elicitation、认证刷新、attestation 与时间请求等服务端调用。当前 PWA 沿用未知交互请求的明确错误回复，不宣称全部 11 种请求均有界面支持；既有命令/文件审批和问题回答继续有独立回归。

本项覆盖指定版本的协议和隔离状态库启动兼容。真实正在运行的任务、Windows/手机交接、生产 daemon 升级、历史数据迁移和实机行为仍按改进计划的 R04/R05、R10、R14/R15 分别验收。
